# PaperPulse 项目复盘

## 目标

用一个可运行的计算机论文 Agent 验证 Pi SDK、MCP、SQLite RAG、Prompt/Skill 和 Eval 的完整调用链。产品目标是输入研究问题后返回最多 15 篇 CCF A/B/C 来源论文，并基于可见检索片段归纳方法与结论。

## 已完成的关键决策

- 让 LLM 负责理解问题、生成检索词和归纳，CCF 来源判断由确定性数据库规则完成。
- 将 CCF PDF 解析为结构化 JSON，再导入 SQLite；不把整份 PDF 每次塞入模型上下文。
- 搜索按 CCF A、B、C 扩展，严格过滤后不足 15 篇时如实返回。
- 使用 MCP 隔离外部论文数据能力，Pi Agent 只获得受限业务工具。
- 从 Pi SDK 的消息事件读取真实 Token 与模型费用，为每次运行生成 Trace。

## 失败与修正

### 页面更新后仍显示旧内容

浏览器缓存导致用户点击旧页面时按钮行为与后端不一致。服务端首页增加 `Cache-Control: no-store`，修改后用真实浏览器重新加载并执行完整链路。

### “最新论文”与结果时间不一致

只依赖检索页默认排序时会混入较早结果。检索先使用 Scholar 日期排序，再在 CCF 严格过滤不足时回退扩大召回；最终结果统一按发表日期排序。

### “顶刊”定义过于主观

最初的“顶刊”没有可复现标准。项目改用用户提供的 CCF 2026 目录，保留 A/B/C，并在 SQLite 中保存目录版本、来源 URL、SHA-256 和页码。

### 测试只能证明代码能运行

最初 7 个测试主要覆盖工程链路。现在增加固定标准答案的离线 Eval，单独报告领域路由、来源匹配和检索式指标，同时明确它仍未覆盖实时召回和归纳忠实度。

## 当前可量化指标

- CCF 目录：681 条结构化期刊/会议记录
- 目标返回：每次最多 15 篇，通过 CCF A/B/C 严格过滤
- 运行指标：run ID、模型/MCP/Scholar 调用次数、Token、费用、总耗时和步骤 Span
- Memory：SQLite 持久化长期偏好、研究历史与论文反馈，支持召回、写入和遗忘
- 离线 Eval：10 个领域样本、12 个来源样本、2 个检索式样本、2 个连续记忆行为

具体分数以 `npm run eval` 生成的 `data/eval-latest.json` 为准，复盘文档不手工复制容易过期的数字。

## 下一阶段

1. 人工标注 30–50 个问题及相关论文，评估 Recall@15、Precision@15 和 CCF 匹配错误。
2. 为归纳建立“每条结论是否有摘要证据”的忠实度标注，并使用独立模型 Judge 后抽样人工复核。
3. 根据 Trace 比较关键词数量、搜索轮次和模型选择对成本与召回率的影响。
4. 增加服务端限流、认证、Secret 管理和公开部署。
5. 将收藏、跳过、阅读反馈转化为线上质量指标，并评估反馈重排对 Precision@15 的影响。
